## 2. Чи варто виносити частину даних

| Група даних | Як з нею працюють | Чи варто NoSQL |
|---|---|---|
| Каталог: книги, автори, видавництва, жанри, примірники | читають набагато частіше, ніж змінюють; картка книги в SQL збирається з 6 таблиць | так, документна база, якщо види книг мають різні поля |
| Видачі, бронювання, штрафи, оплати | гроші й статуси, кілька таблиць змінюються в одній транзакції | ні, потрібні транзакції та зовнішні ключі |
| Читачі й абонементи | пов'язані з видачами й оплатами | ні |
| Персонал і ролі | мало даних, змінюються рідко | ні, вигоди немає |
| Тимчасові дані: бронь місця в читальній залі, лічильники переглядів, кеш картки | живуть недовго, втрата не критична, важлива швидкість | так, key-value |

За вимог першої лабораторної всі дані зручно тримати в PostgreSQL: обсяг невеликий, а облік видач і оплат
потребує транзакцій. NoSQL стає доцільним, якщо розширити вимоги, тому я додала нову вимогу:
**бібліотека зберігає не лише паперові книги, а й електронні та аудіокниги, і кожен вид має власні поля**
(в паперової книги кількість сторінок, обкладинка й примірники на полиці, в електронної формат і розмір файлу,
в аудіокниги тривалість і диктор).

У реляційній схемі під кожен вид потрібна окрема таблиця, а картка книги збирається з 9 таблиць.
У документній базі кожна книга є одним документом зі своїм набором полів. Тому каталог я перенесла в MongoDB,
а облік видач і оплат лишила в PostgreSQL. Чи дає це виграш у швидкості, перевіряє пункт 5.

## 3. Каталог у MongoDB

Колекція `books`, один документ на книгу. Видавництво, жанр, автори й примірники вкладені в документ,
а поля конкретного виду лежать у `paper`, `ebook` або `audio`. Документ містить лише поле свого виду.
Приклад паперової книги з бази (примірники скорочено):

```js
{
  _id: 10,
  isbn: '978-000000010',
  title: 'Дім північного вітру',
  type: 'paper',
  publishYear: 2024,
  publisher: { _id: 21, name: 'Смолоскип' },
  genre: { _id: 3, name: 'Драма' },
  authors: [
    { _id: 38105, fullName: 'Софія Гуменюк' },
    { _id: 95141, fullName: 'Олена Дяченко' },
    { _id: 182706, fullName: 'Галина Поліщук' }
  ],
  paper: { pagesCount: 859, coverType: 'hard' },
  copies: [
    { inventoryNumber: 'INV-00000011', status: 'available' },
    { inventoryNumber: 'INV-00000012', status: 'written_off' }
  ]
}
```

В електронної книги замість `paper` і `copies` є лише `ebook: { fileFormat: 'pdf', fileSizeMb: Decimal128('12.29') }`,
а в аудіокниги `audio: { durationMinutes: 738, narrator: 'Людмила Поліщук' }`.

Код: [MongoCatalogStore.cs](src/LibraryNoSql.Bench/MongoCatalogStore.cs).
Індекси: `{ 'genre._id': 1, publishYear: -1, _id: -1 }` для сторінки каталогу
і `{ 'authors._id': 1 }` для пошуку за автором (індекс по полю всередині масиву).

## 4. Той самий каталог у PostgreSQL

Схема: [sql/schema.sql](sql/schema.sql). Колекція `books` відповідає 9 таблицям:

| Частина документа | Таблиця |
|---|---|
| `_id`, `isbn`, `title`, `type`, `publishYear` | `books` |
| `publisher` | `publishers` |
| `genre` | `genres` |
| `authors[]` | `authors` + таблиця-зв'язка `book_authors` |
| `paper` | `paper_book_details` (1:1 з `books`) |
| `ebook` | `ebook_details` (1:1) |
| `audio` | `audiobook_details` (1:1) |
| `copies[]` | `book_copies` |

Код: [SqlCatalogStore.cs](src/LibraryNoSql.Bench/SqlCatalogStore.cs). Індекси створені на тих самих полях, що й у MongoDB,
плюс індекси на зовнішніх ключах для JOIN (у MongoDB ці дані вкладені в документ, тому там такі індекси не потрібні).

## 5. Порівняння швидкодії

### Як я міряла

- **Однакові дані.** Генератор ([DataGenerator.cs](src/LibraryNoSql.Bench/DataGenerator.cs)) з фіксованим seed створює
  один набір, і цей самий набір завантажується в обидві бази. Частки: 60% паперових книг, 25% електронних, 15% аудіо;
  1–3 автори на книгу; 1–5 примірників на паперову книгу.
- **Дані вигадані, але схожі на справжній каталог.** Реального каталогу на мільйон книг у мене немає, тому дані
  згенеровані. Видавництва — 30 справжніх українських видавництв, назви книг складаються з шаблонів під жанр
  («Вбивство у Львові» для детективу, «Підручник з фізики» для навчальної літератури), книга виходить не раніше,
  ніж авторові виповнилося 18. Для швидкості важить не зміст назв, а кількість записів, довжина полів і розподіли
  (скільки авторів і примірників у книги), тому їх я задала явно.
- **Три обсяги: 10 000, 100 000 і 1 000 000 книг.** Мільйон книг — це 1,3 млн рядків `book_authors` і 1,8 млн примірників.
  Кілька обсягів показують, як різниця змінюється з ростом даних.
- **Однакові відповіді.** Перед замірами програма ставить обом базам ті самі 401 запит і порівнює відповіді.
  Усі збіглися на всіх трьох обсягах, тобто обидві реалізації роблять одне й те саме.
- **Однакові умови.** Обидві бази в Docker з лімітом 4 CPU і 2 ГБ пам'яті; кеш даних обох по 512 МБ
  (`shared_buffers` у PostgreSQL, WiredTiger у MongoDB). Один клієнт (C#, Npgsql і MongoDB.Driver) на тій самій машині.
- **Однакова надійність запису.** PostgreSQL на commit чекає запису WAL на диск, тому для MongoDB я ввімкнула
  `journal: true`: запис підтверджується лише після потрапляння в журнал на диску.
- **Індекси використовуються.** Перевірила планами запитів: у PostgreSQL `Index Only Scan using ix_books_genre_year`,
  у MongoDB для сторінки каталогу переглянуто 20 документів з 1 000 000 (`IXSCAN`, без повного перебору).
- **Статистика.** Кожен сценарій спочатку прогрівається (50 викликів, не враховуються), потім 500 вимірів для читання,
  300 для запису й 50 для важкої агрегації. Кожен виклик міряється окремо, у таблиці медіана і p95.
  Обидві бази отримують однакову послідовність вхідних даних.
- **Повторюваність.** Замір на мільйоні книг я запускала двічі. Медіани між запусками відрізнялися до 15%,
  але в кожному сценарії переможець лишився той самий.

### Сценарії

| Сценарій | Чому саме він |
|---|---|
| Картка книги за id | найчастіша дія читача; у SQL з'єднання 9 таблиць, у MongoDB один документ |
| Сторінка каталогу: жанр + роки, 20 найновіших | типовий перегляд каталогу з фільтром і сортуванням |
| Усі книги автора | у SQL через таблицю-зв'язку, у MongoDB за полем усередині масиву |
| Кількість книг за жанрами | звіт по всьому каталогу: читає всі книги |
| Додавання однієї книги | у SQL до 4 таблиць в одній транзакції, у MongoDB один документ |
| Перейменування автора | у SQL змінюється один рядок, у MongoDB ім'я скопійоване в кожну книгу автора (у середньому 6,5 книги) |

### Висновки

- **Читання за ключем і за індексом** в обох базах триває менше за мілісекунду. Більшу частину цього часу
  займає дорога запиту від клієнта до бази й назад, а не сама робота бази. На 10 000 книг усі три запити
  швидші в PostgreSQL (у 1.2–1.6 раза), а з ростом даних різниця зменшується до 10–15%.
  Картку книги на мільйоні швидше віддає MongoDB: це один документ, а в PostgreSQL запит робить кілька пошуків
  по індексах для JOIN, і з ростом таблиць кожен такий пошук стає дорожчим. Сторінку каталогу й книги автора
  навіть на мільйоні трохи швидше віддає PostgreSQL: для списку йому потрібні лише вузькі рядки `books`,
  а MongoDB дістає документи цілком і вже потім відкидає непотрібні поля.
- **Агрегація по всьому каталогу** — сильна сторона PostgreSQL: у 2–2.3 раза швидше на 10 000 і 100 000 книг
  і в 6.4 раза на мільйоні. PostgreSQL рахує по вузькій таблиці `books`, а MongoDB мусить прочитати й розпакувати
  кожен документ цілком, разом з авторами й примірниками.
- **Додавання книги** швидше в MongoDB (у 1.4–1.9 раза): один документ замість вставок у 3–4 таблиці в транзакції.
- **Перейменування автора** швидше в PostgreSQL (у 2.5–2.9 раза): там ім'я зберігається в одному рядку,
  а в MongoDB його копія лежить у кожній книзі автора. Це ціна вкладених даних.
- **Місце й завантаження.** MongoDB займає в 3–4 рази менше місця (WiredTiger стискає дані) і завантажує
  набір приблизно вдвічі швидше, бо не перевіряє зовнішні ключі й пише одну колекцію замість 9 таблиць.

Загальний висновок: для каталогу MongoDB не дає великого виграшу в швидкості читання на цих обсягах.
Її переваги — гнучка схема для різних видів книг, простий запис цілої книги й менший обсяг даних.
PostgreSQL кращий для звітів і для змін даних, які повторюються в багатьох записах.
Тому поділ із пункту 2 виправданий: каталог у документній базі, облік і звіти в PostgreSQL.

### Що не тестувалося і чому

- **Паралельне навантаження.** Я міряла затримку одного запиту від одного клієнта, бо саме її відчуває читач.
  Тест із багатьма одночасними клієнтами — окреме завдання, де результат сильно залежить від налаштувань пулів з'єднань.
- **Мережа між серверами.** Клієнт і бази на одній машині. Мережева затримка додалася б до обох баз однаково
  і лише приховала б різницю між ними.
- **Дані, що не вміщуються в пам'ять.** На мільйоні книг PostgreSQL займає 609 МБ, тобто вже більше за свій кеш
  у 512 МБ, і частину даних читає з кешу операційної системи. Для обсягів у десятки ГБ потрібна інша машина.

## 6. Redis

Redis — key-value база, яка тримає дані в оперативній пам'яті. Вона підходить для даних, що живуть недовго
й мають читатися дуже швидко. Скрипт [redis/basics.sh](redis/basics.sh) виконує базові запити на прикладах
бібліотеки, а його вивід збережено в [redis/output.txt](redis/output.txt).

| Тип даних | Команди | Приклад у бібліотеці |
|---|---|---|
| Рядок | `SET`, `GET`, `DEL`, `EXISTS` | назва книги за ключем |
| Рядок із терміном дії | `SET ... EX 900 NX`, `TTL`, `EXPIRE` | місце в читальній залі тримається 15 хвилин; `NX` не дає двом читачам зайняти одне місце |
| Лічильник | `INCR`, `INCRBY` | кількість переглядів сторінки книги |
| Hash | `HSET`, `HGET`, `HGETALL`, `HINCRBY` | кешована картка книги на годину |
| List | `LPUSH`, `LTRIM`, `LRANGE` | 3 останні книги, які відкривав читач |
| Set | `SADD`, `SISMEMBER`, `SINTER` | улюблені книги, спільні улюблені двох читачів |
| Sorted set | `ZINCRBY`, `ZREVRANGE ... WITHSCORES`, `ZSCORE` | топ книг за кількістю видач |
| Робота з ключами | `TYPE`, `SCAN ... MATCH`, `TTL` | пошук ключів за шаблоном, перевірка, що ключ із терміном дії зник |

## Запуск

Потрібні Docker і .NET 10 SDK. Усі команди виконуються з кореня репозиторію.

1. Запустити PostgreSQL, MongoDB і Redis (схема PostgreSQL створюється автоматично при першому запуску):

   ```bash
   docker compose up -d
   ```

2. Заміри (аргумент — кількість книг, результат у `results/results-<кількість>.md`):

   ```bash
   dotnet run -c Release --project src/LibraryNoSql.Bench -- 100000
   ```

3. Базові запити Redis:

   ```bash
   bash redis/basics.sh
   ```
